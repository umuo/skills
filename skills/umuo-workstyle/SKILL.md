# umuo 的个人协作偏好

这是从用户跨项目的 Codex 会话中整理出的默认偏好。当前明确要求优先；遇到项目约束，遵循项目规则。只应用与本次任务相关的部分，不把历史任务当成新的操作授权。

## 协作与交付

- 默认用中文交流和编写用户文档，代码、协议字段和技术名称保留原名。简短进度与结果说明即可；学习材料按读者需要展开。
- 用户说“帮我做”“优化”“修复”时，推进到可使用、可验收的结果。已经认可的方案不反复询问；“继续”承接尚未完成的任务和约束；缺少进度上下文时先查当前工程或任务记录，不根据这份偏好猜测做到了哪一步。用户只要设计、调研或建议时，交付相应成果。
- 保持专业判断。用户给的例子通常不穷尽需求；识别通用问题，补充完成本次目标所必需的遗漏并解释取舍。可选的新功能作为建议，不擅自扩大实施范围。对于值得商榷的意见，先给有依据的建议，用户明确决定后落实。

## 轻量 SDD：需求、实现与验收

- 新项目和复杂功能采用轻量规格驱动开发（Spec-Driven Development）：先明确需求与验收标准，再结合 spike 完成技术选型和必要设计，按规格实现，最后对照验收。规格可以随调研细化，不要求一次写完所有细节。区分用户明确要求的 MVP、完整移植和生产化迭代，不自行降级交付。
- 规格写清目标与使用场景、本次范围与不做的内容、关键行为与必要的异常或边界处理、实际约束，以及可观察、可验证的验收标准。例如“支持导出”应细化为目标格式、要保留的内容和验证方式；避免只写“正常运行”“体验良好”。区分用户明确要求、合理假设与待确认问题，只澄清会实质影响范围、架构或验收的关键缺口。
- 规格的篇幅与任务规模相称。简单修改或明确的 Bug 修复，用简短说明记录预期行为与验证方式即可；复杂工作沿用项目已有文档体系，没有约定时可在 `docs/` 保存一份简洁的规格，包含必要的方案、选型理由与验收清单。已有清晰需求或规格时直接复用并补缺，不机械创建多份文档，不默认新增规格审批环节。
- 实现围绕验收标准推进，复杂任务先梳理必要的结构与接口，并拆成可验证的步骤。用户调整需求或调研发现约束变化时，同步更新相关规格、设计与验收标准，说明对范围和方案的影响；不能用修改验收标准掩盖未完成的需求，也不能把实现中想到的可选功能自动加入范围。
- 完成时逐项核对验收标准，验证用户实际使用的路径，报告完成内容、验证证据以及未完成或未验证的部分。编译通过不能代替使用效果验证，小修改不扩大为全产品验收。SDD 不强制采用 TDD：按行为风险选择自动化测试、实际运行或人工检查；业务规则、复杂状态变化和容易回归的逻辑优先用测试覆盖，修复明确的 Bug 时优先增加可复现问题的测试。

## 方案与实现

- 遇到新的需求（新项目、新功能或新能力接入），在设计和编码前先做 spike：先检查当前工程已有能力与项目约束，再检索现成、成熟的开源项目与组件，评估能否直接使用、二次开发或集成，避免默认让 AI 从零实现。用户已经指定方案时围绕该方案验证；当前任务明确不需要调研时遵循其要求。
- Spike 不只列项目名称或按 star 数推荐。结合需求覆盖、维护状态、文档与示例、许可证、技术栈兼容性、接入成本和可扩展性判断成熟度；对关键能力查看源码或做必要的最小验证。结论写清需求匹配、候选链接、推荐方案、需自行实现的缺口与验证结果，区分已验证事实和待验证判断。调研深度与需求规模相称；已有证据足以选型就推进，不无限寻找“最成熟”的项目。无法联网或验证时说明限制，不把未搜索当成没有现成方案。
- 在现成系统二开、集成组件与自行实现之间，按需求匹配和长期维护成本选择；不为了复用整个项目而引入比需求更复杂的系统。只有现有方案不适合的部分才自行实现，并说明原因。调研完成后继续推进已授权的实施，不停在候选清单。既有功能的小修复不必重复全面 spike；未知机制仍查官方文档与成熟实现。
- 按业务领域和职责组织包、目录与模块。Java 代码应合理分包，让相关功能集中、职责边界清楚，避免所有类堆在同一个包，或把无关逻辑塞进一个大类、长方法。沿用项目现有的组织规范，不机械套用固定分层或拆分过多模块。
- 架构以可读性、可维护性和可扩展性为目标，遵循单一职责、高内聚、低耦合等原则。明确模块职责与依赖方向，将业务逻辑与外部接口、存储等实现细节合理隔离，避免循环依赖和牵一发而动全身的修改。
- 根据实际变化点使用接口、组合或合适的设计模式，使新增功能优先通过清晰的扩展点实现。抽象应有明确收益，不为使用设计模式而设计，也不为假想需求增加复杂框架。解决通用问题，不只针对用户给的单个样例打补丁。
- 开发新项目时，在设计和编码前结合 spike 完成技术选型。先明确业务需求、交付范围与关键约束，再选择实际需要的语言与运行时、框架、存储、构建和部署方案；不为凑齐技术栈引入无用组件。用户熟悉 Java、Agent 开发，但不代表所有项目都必须使用 Java。已有工程沿用合理的技术栈与版本约束；用户指定技术时尊重其选择，并说明适用性与必要的取舍。
- 每项关键技术选择都要给出对应的、与当前项目有关的理由：解决哪个需求，为什么适合当前约束，相较合理替代方案的优势，以及带来的成本、限制或风险。按相关性评估生态与维护状态、兼容性、开发与运维成本、性能与规模、许可证及团队熟悉度，不能只用“流行”“成熟”“我熟悉”作结论。存在实质竞争的方案时简要对比；理由依赖版本能力、性能或兼容性时查官方资料或做最小验证，区分事实、假设和待验证项。
- 实施前向用户说明技术选型结论，可用“技术／用途／选择理由／替代方案与取舍”的简表；复杂项目将结论写入项目技术方案或决策记录，简单项目简短说明即可。证据足以支持选择后继续已授权的开发，不默认新增审批环节；只有影响选型的关键需求或约束无法确定时才请求澄清。
- 配置尽量统一管理，避免多个功能或节点重复填写同一套参数。新增配置写清中文说明、默认值、空值含义和配置位置；示例应当能真正跑通。
- 代码遵循项目及语言生态的命名、格式和组织规范，类与方法职责聚焦，命名表达业务含义，避免挤成单行或堆砌难以理解的逻辑。复杂逻辑、扩展点和非显然的设计理由用适量中文注释说明。

## 公开内容与 Git

- 公开代码、README、示例参数和日志片段不能泄露真实密钥、个人信息、本机用户名与私有目录结构。使用相对路径、环境变量或占位符；本地配置与公开模板分开，并检查忽略规则及待提交文件。
- 用户提供真实路径用于本机操作，并不表示可以原样写入公开文档。聊天中的本地文件链接可以使用准确路径。
- 提交、推送、部署、发布、改写历史和服务器操作以当前任务授权为准，不能从历史会话继承许可。已授权连续提交时，按有意义的完成阶段及时提交。采用用户指定的部署平台。

## 按任务读取细节

- 写技术教程、学习源码指南或项目文档（默认用 MkDocs 与 Mermaid 插件渲染）：读取 [技术学习与文档](references/task-preferences.md#技术学习与文档)。
- 做界面、移动适配、打印或导出：读取 [产品与视觉交付](references/task-preferences.md#产品与视觉交付)。
- 开发 Agent、LLM 集成或跨平台版本：读取 [Agent 与模型接入](references/task-preferences.md#agent-与模型接入)。
- 简单问答与小修改不必加载无关细节。用户明确要求记住或修改长期偏好时更新对应规则；本次项目的特殊要求只用于本次任务，不自动追加为全局规则。修订时合并或替换旧规则，避免矛盾和重复；不要在每个会话重新扫描历史。
