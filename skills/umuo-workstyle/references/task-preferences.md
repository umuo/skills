# 按任务应用的偏好

只使用当前任务相关的部分。以下是用户工作方式的归纳，不要求每个项目实现所有能力。

## 技术学习与文档

学习陌生框架、底层原理时，先补必要的先修概念，再连接到实际代码。解释深度依据当前问题和用户反馈调整，避免只剩定义或重复已经掌握的基础。

- 先解释解决什么问题，再介绍必要概念，用具体输入贯穿完整执行链路，最后映射到源码入口、关键类和调用顺序。
- 讲 HTTP API 时，从真实请求、响应、流式事件和服务端处理链路入手；SDK 可作为补充，不能代替协议原理。
- 源码指南基于实际代码，提供“从哪里开始、下一步跟哪个方法、如何验证”的阅读路径。对阅读该源码所需的陌生前置技术，补原理、图和可运行的小例子。
- 补充用户尚未想到的相关知识点，但按学习路线安排，避免孤立堆积名词。文档有连贯导航，使读者能找到已经写过的内容。
- 项目文档通常适合保存在 `docs/`，README 作为入口。用户多次使用 MkDocs；已有站点则沿用其体系，新建技术知识库可优先考虑 MkDocs。
- 使用手册说明能干什么、怎么启动、怎么配置、怎么扩展，并给最小运行示例。配置项列出语义、单位、默认/空值行为；SDK 扩展点给具体代码示例。
- 图要在实际目标中正常渲染，不能只留下无法显示的 flowchart 文本。依目标环境选择受支持的 Mermaid、SVG 或图片，并验证构建与显示。

## 产品与视觉交付

- 重视 UI 质量、信息密度与操作便利；不要反复套用同一种模板风格。根据用途、参考和用户反馈设计，风格一致，不只局部加图标或装饰。
- Web 产品通常需要同时适配手机和电脑。检查真实交互：触摸、滚动、输入、侧栏折叠、弹窗，以及相关的全屏、音频或播放行为；移动适配不止是缩窄布局。
- 重要状态应直观可辨，图表有轴、图例和必要提示。展示面向用户的内容，避免把内部技术机制直接堆在主界面。
- 动画服务于操作反馈。交换、拖动、掉落、加载等过程要看得见且节奏合适，不能完成状态跳变就算实现了动画。
- 任务涉及调试信息、工具参数或执行轨迹展示时，默认折叠，允许展开查看，避免挤占主要内容。消息与工具事件按真实发生顺序显示；不为无关产品额外增加调试面板。
- 试卷、简历、笔记和漫画等导出结果，需要查看实际输出，检查纸张尺寸、字体、分页、边距、留白与可打印性。尺寸和内容要求以本次任务为准。

## Agent 与模型接入

- 调研或实现 Agent Loop、Tool、State、上下文工程、Skills、MCP 与 Harness 时，参考成熟项目的真实机制，避免仅按名字猜测设计。
- 普通聊天与 Agent 模式的职责要清楚；在用户要求这种划分时，普通聊天不偷偷注入工具或无关记忆。Planning 可以作为 Agent 自主选择的工具，不强制每轮执行或要求用户选择内部架构。
- 记忆应面向通用内容，支持用户查看和管理；不要因“记住博客网址”这个例子把整个系统限制为网址收藏。
- LLM 接入优先支持可配置的兼容接口，集中管理 base URL、API key 和 model。按照实际需要支持流式、非流式及其他 Provider，不把所有模型接口能力默认视为一致。
- 处理流式工具调用的片段聚合、事件顺序、参数错误及异常反馈；不能把每个 JSON 片段当成独立工具显示。扩展上下文处理时，考虑裁剪、压缩与工具输出过长的可靠处理。
- 跨平台移植应列清功能对照，确认源平台已有的工具、记忆和配置等功能在目标平台真实可用；用户要求完整移植时，不用静默简化掩盖缺失。
- 辅助能力失效时按任务约定降级，例如可选 rerank 不可用时跳过；安全策略的拒绝/放行行为需按当前要求确定，不能套用普通检索的降级逻辑。
